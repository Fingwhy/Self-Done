# STM32 智能桌面宠物 · 项目总结

> 对象：四足桌面机器狗（STM32F103C8T6）
> 版本：硬件 V1.2.1（2025-08），软件最后更新 2025-08
> 平台：嘉立创 EDA + Keil MDK + SolidWorks
> 整理时间：2026-10（据开源工程、实物与当时笔记回填）

---

## 一、项目目标

做一只**放在桌上、能听懂人话、会自己动**的小狗。

最早只是想试试舵机能不能做出"走路"的感觉，做完一个舵机的点头动作之后停不下来，于是定了三条线：

| 线 | 内容 | 结果 |
|---|---|---|
| **结构** | SolidWorks 建模四足 + 尾巴，3D 打印件，舵机内置 | 完成，四足 + 摆尾 |
| **电子** | 自绘 PCB：电源、舵机排针、OLED、语音、蓝牙、呼吸灯 | 走完 4 个版本 |
| **软件** | 舵机 PWM、动作帧表、串口指令解析、OLED 表情 | 完成 12 个动作 |

定下的验收标准很朴素：**放在桌上，喊一声它抬头打招呼，说"前进"它往前走两步不散架。**

## 二、系统架构

```
        麦克风                       手机
          │                           │
   ┌──────┴──────┐              ┌─────┴─────┐
   │ SU-03T1 /   │  USART1      │ 蓝牙透传  │  USART3
   │ CI-03T 语音 │─────────┐    │   模块    │────┐
   └─────────────┘         │    └───────────┘    │
                           ▼                     ▼
                    ┌──────────────────────────────────┐
                    │        STM32F103C8T6             │
                    │  指令解析 → 动作状态机 → 帧调度   │
                    └───┬──────────┬───────────┬───────┘
                        │ TIM PWM  │ 软件 I2C  │ GPIO
                        ▼          ▼           ▼
                 ┌───────────┐ ┌────────┐ ┌──────────┐
                 │ 5 路舵机  │ │ OLED   │ │ 四角呼吸灯│
                 │ 四足+尾巴 │ │ 表情   │ │ 电量 ADC │
                 └───────────┘ └────────┘ └──────────┘
                        │
                  5V 充放电模块 ← 3.7V 锂电
```

**关键定位**：主控用现成的最小系统板，板上只做"接口板"的事——把电源、舵机、屏幕、语音、蓝牙的线全部收进一块 PCB。好处是调试期随时换板、直接烧程序；代价是体积大、空间利用率低（后面复盘里认了这条）。

## 三、关键设计决策

### 1. 为什么用舵机而不是电机 + 编码器

桌面宠物的动作是"摆姿态"，不是"精确走轨迹"。舵机自带位置闭环，一根 PWM 就能指定角度，五路就是五根线。换成直流电机 + 编码器，成本、体积、调试量都会翻几倍，收益却只在"能连续转"，而这个项目不需要。

### 2. 为什么五路，而不是八路

四足理论上八自由度（每条腿两个关节）动作更自然，但：

- 8 路舵机的电流峰值把 5V 充放电模块直接压死（后来 5 路都已经出问题了）
- 8 个关节的动作帧要一帧一帧调，工作量翻倍
- 四足各一自由度已经能做出"抬腿—前摆—落地"的走路感

最后定 5 路：四足各一 + 尾巴一路。尾巴这一路性价比最高，摇起来情绪感立刻就有了。

### 3. 电源为什么一开始绕了弯

V1.0 的电源是：3.7V 锂电 → 5V 充放电模块 → 板上 AMS1117 降到 3.3V 给 MCU，5V 直接给舵机。

问题在于**舵机和 MCU 共用一个 5V 源**。舵机启动瞬间的浪涌把 5V 拉下去，AMS1117 的输入跟着掉，MCU 复位，语音模块也跟着重启——表现就是"一喊它动，它先抽一下，然后不理你"。

V1.1 的改法是先把 AMS1117 删掉（最小系统板自带 LDO，重复降压纯属浪费压差和板面），但这只解决了板面，没解决根源。根源在充放电模块的输出能力，见「六、已知问题」。

### 4. 串口为什么是"共用烧录口"

V1.0 每次烧程序要拔蓝牙、拔语音、插 CH340，很烦。V1.1 起把语音模块和主控的下载线并到一个排针上，靠丝印标注区分，烧录时不用拆线。

代价是丝印必须非常小心：**板子上标 TX 的地方是给对面模块的 RX 用的**。V1.2.1 直接把两处丝印统一成"TX 接 RX、RX 接 TX"的交叉写法，并在丝印上标了复用脚位，避免自己半年后看不懂。

## 四、软件结构

```
main.c
 ├─ 外设初始化：PWM(5ch) / USART1 / USART3 / 软件I2C / ADC
 ├─ 指令解析：串口中断收字节 → 拼帧 → 投递指令码
 ├─ 动作状态机：IDLE → ACTION(n) → IDLE，SLEEP 可打断
 ├─ 帧调度：定时器 20ms 节拍，按帧表插值写 PWM 比较值
 └─ 显示：OLED 表情随状态切换（待机/执行/睡眠）
```

三层解耦是刻意的：

- **指令层**只认指令码，不关心指令从语音来还是从蓝牙来——两个串口收到的帧格式做成一致，解析函数复用
- **动作层**只认动作编号，不关心动作是谁触发的
- **执行层**只认"第几路、多少度"，不关心当前是什么动作

这样加一个新动作 = 在帧表里加几行，加一个新指令 = 在映射表里加一行，都不用动状态机。

## 五、指标

| 项 | 数值 |
|---|---|
| 舵机通道 | 5（PA0 左前 / PA1 右前 / PA2 左后 / PA3 右后 / PA6 尾巴） |
| PWM | 50Hz，脉宽 0.5~2.5ms 对应 0~180° |
| 动作数 | 12（立正、前进、后退、左转、右转、摇尾巴、趴下、蹲下、睡觉、向前跳、打招呼、伸懒腰） |
| 控制源 | 离线语音（USART1）+ 蓝牙（USART3），指令码共用一套 |
| 显示 | 0.96" OLED，128×64，I2C |
| 板卡 | 2 层，V1.2.1 为最终版 |
| 供电 | 3.7V 锂电 → 5V 充放电模块（舵机）/ 3.3V（MCU） |

> 舵机为 9g 级微型舵机，具体型号以实物为准；早期没留 BOM，这也是后来被自己吐槽的地方。

## 六、已知问题（不遮掩）

### 1. 充放电模块电流不够 —— 最致命的一条

四路舵机同时动作时 5V 明显跌落，实测表现为 MCU 复位、语音模块重启。现象是"喊它，它抽一下然后装死"。

根因是充放电模块的持续输出电流不到五路舵机峰值的总和。舵机堵转电流远大于空载，动作帧里几个关节同时起动的瞬间就是最坏情况。

**正确做法**：舵机单独一路大电流 buck（5V/3A 以上）+ 每路舵机就近加 100~470µF 储能电容，MCU 与舵机分开供电、单点共地。当时没做，是在这块板子上最大的教训。

### 2. 开发板方案的空间浪费

最小系统板占了板面近一半，还多了一整套排针和杜邦线。装在结构里线容易顶到舵机臂。这是"先跑通、再优化"的代价，但下次会先画一体板。

### 3. BOM 没有规范整理

第一次画 PCB，元件是边选边加的，BOM 表事后补不齐，给别人复刻添了麻烦。

### 4. 原理图与 PCB 曾经不一致

有几个元件是直接在 PCB 里复制放置的，原理图上没有，导致原理图转 PCB 报错。2025-11-07 重新整理了 V1.2.1 工程，现在转图不报错。

## 七、复盘

做这个项目最大的收获不是"狗会走了"，而是**第一次完整踩了一遍"电路—结构—固件—联调"的全链路**：

1. **电源永远是第一优先级**。功能都写对了，电源一塌，现象会伪装成"程序跑飞""模块坏了""代码有 bug"，排查方向全错。
2. **丝印是给未来的自己看的**。TX/RX 交叉、复用脚位、排母朝向，写清楚一次省掉无数次万用表。
3. **动作调试要有工具**。手动改角度—编译—烧录—看效果，一轮两分钟。后来把"单关节调到指定角度"做成一条串口指令，效率高了一个数量级。
4. **先跑通再优化是对的，但要留优化余地**。开发板方案让我快速验证了所有功能，但也把体积和布线锁死了。

如果重做一版，顺序会是：先定电源预算（五路舵机峰值电流 × 1.5 余量）→ 再定结构 → 再画一体板 → 最后写固件。现在的做法是反过来的。
