# 智能家居魔法系统：项目计划报告

版本：v0.1  
日期：2026-11-05  
状态：准备开始  
实施方式：本人独立实施，开源项目仅作为技术参考。

## 1. 目标与范围

设计一支手持魔法棒，识别预定义挥动手势，经本地网络触发智能家居动作。由本人完成需求分析、选型、接线、固件、数据集、模型、联动、测试及后续结构设计，形成可解释、可复现的嵌入式项目。

首版以跑通完整链路为目标：按键启动采样 → 手势识别 → MQTT 事件 → Home Assistant 自动化 → 指定灯或智能插座动作。当前所有硬件、性能、预算和工期均为规划，未实测。

首版范围：3 种有效手势、无效动作拒识、灯具开关、一组场景、状态反馈和基本异常处理。第一版不实现任意目标指向识别，不直接设计市电执行电路。语音咒语、红外、蓝牙键鼠、多房间定位及多人通用模型列为后续扩展。

## 3. 系统架构

```text
按钮 + MPU6050
      ↓ I²C / GPIO
ESP32-C3：采集 → 分段 → 预处理 → 推理 → 置信度与拒识 → 事件发布
      ↓ Wi-Fi / MQTT
本地 MQTT Broker → Home Assistant 自动化 → 已接入的灯 / 智能插座
      ↑
执行反馈 / 超时反馈 → 魔法棒 LED（后续可增加震动）
```

魔杖负责报告手势，中枢维护手势与设备的映射。首版绑定固定设备，不使用 IMU 推断所指向的灯。区分“识别成功”“消息已发送”“设备已反馈”，避免只发出消息就显示执行成功。

## 4. 硬件初选

| 模块 | 拟选方案 | 实施前核查 |
| --- | --- | --- |
| 主控 | ESP32-C3 开发板，优先带 USB 调试接口 | Flash、可用 GPIO、USB 与下载方式、供电 |
| IMU | MPU6050 模块 | I²C 电平、供电电路、地址、器件状态、固定方向 |
| 输入 | 一个独立按钮 | 上拉方式、消抖、采样窗口触发 |
| 反馈 | LED + 限流电阻；震动后置 | 驱动电流；电机需驱动级，不能直接挂 GPIO |
| 原型供电 | USB 低压供电 | 稳定性、线缆与接头受力 |
| 家居中枢 | 现有电脑 / 树莓派 / 小主机 | 可持续运行 Home Assistant 与 Broker |
| 执行设备 | 可本地接入的灯或成品智能插座 | 型号、协议、是否依赖云、状态反馈 |

先模块验证，再设计 PCB 和外壳。原型材料按“主控 + IMU + 按钮 + 指示灯 + 连接材料”列采购清单；实际询价后形成预算，不将上游模块成本视为整机成本。电池版本另行评估保护、充电、电源切换和外壳空间。

## 5. 软件与接口规划

固件优先评估 ESP-IDF；如果推理库和开发板组合不兼容，先用 Arduino 验证算法，记录切换理由。确定方案后锁定框架、编译器、依赖库和 Python 环境版本。

建议模块：imu、button、capture、preprocess、inference、gesture_filter、mqtt_client、feedback、config。采集、推理和网络发送分离；网络异常不能阻塞传感器或导致无限排队。

初始采样频率以 100 Hz 为试验起点，记录实际时间戳及丢样；窗口长度和模型输入形状由采集数据决定。采集加速度和角速度六轴数据，但最终模型可根据实验选择通道。传感器单位、轴向、归一化参数、裁剪和补齐必须在训练与固件端保持一致。

状态机拟定：空闲 → 按键采集 → 松开结束 / 超时结束 → 预处理 → 识别 / 拒识 → 发布 → 冷却 → 空闲。设置最短、最长动作长度，避免空窗口与无界采集。

MQTT 初步约定（实现前验证）：

```json
{
  "schema": 1,
  "device_id": "wand_01",
  "session_id": "boot-session",
  "event_id": 1,
  "gesture": "light_on",
  "confidence": 0.95,
  "model_version": "v0.1"
}
```

事件主题：`magic_home/wand_01/gesture`，不保留历史手势消息（retain=false）。状态主题与手势事件分开。事件编号配合启动会话标识用于去重；冷却时间不能代替网络去重。连接恢复后不补发过期控制事件。MQTT 账号和密码使用本地配置，不提交到仓库。优先使用明确的开/关动作，避免重复 toggle 导致状态反转。

## 6. 数据集与模型路线

1. 先选定 3 个差异明显的手势，并用文字和图记录标准动作，暂不追求复杂咒语数量。
2. 每种手势首轮采集约 50–100 次，分多次采集；同时采集拿起、放下、走动、随意摆动等负样本。数量是起点，以验证结果决定补采。
3. 保存原始六轴数据、时间戳、标签、采集批次、设备安装方向和固件版本；原始数据与预处理结果分开保存。
4. 按采集批次划分训练、验证和测试集，避免同一次动作的相邻窗口分到不同集合。最终测试数据不参与阈值调节。
5. 训练轻量 CNN，先建立浮点基线，再量化为 INT8；记录量化前后识别变化、Flash 和 RAM 使用。
6. 设置无效动作策略与识别阈值，记录混淆矩阵、各类识别表现和拒识率。不要强制把所有输入归入有效手势。
7. 固件记录模型版本及预处理参数，使用一组固定样本比较 Python 与端侧输出。

若神经网络效果或部署成本不理想，以阈值规则或 DTW 做对照实验，再决定最终路线。

## 8. 初步验收指标

这些是拟定目标，尚未达成；第一轮基线后可调整，但需记录原因。

| 项目 | 初始目标与测法 |
| --- | --- |
| 有效手势 | 每类至少 30 次独立测试；每类正确识别率 ≥90%，拒识也计为未正确识别 |
| 无效动作 | 至少 100 次负样本测试；有效手势误报率 ≤5% |
| 日常误触 | 非采集状态下携带、拿放累计 30 分钟，不触发家居动作 |
| 联动成功 | 稳定局域网下完成 50 次开/关指令，至少 49 次得到目标状态反馈 |
| 延迟 | 从松开采集按钮到目标状态反馈，P95 ≤1 秒；明确记录测量方法与超时 |
| 重复消息 | 注入重复事件、模拟重连，单事件最多执行一次，不重放旧命令 |
| 稳定性 | 连续运行 2 小时，记录重启、掉线、采样错误和失败次数 |
| 故障表现 | Broker/HA/设备离线时给出失败或超时状态，不显示虚假的成功反馈 |

## 9. 风险与处理

- 手势速度、握姿和 IMU 安装方向不同：固定安装方向、分批采集、补充变化样本。
- 训练与端侧预处理不一致：使用固定输入对照输出，并版本化参数。
- 模型无法泛化：以本人使用为首版边界；跨人使用单独建立测试集。
- ESP32-C3 资源或库兼容问题：P0 先编译最小推理示例，测内存后再决定模型。
- Wi-Fi 断连与消息重复：事件去重、限时、非 retained、旧命令不重放。
- 外壳改变握姿和运动数据：装配后重新验证，必要时补采。
- 执行设备依赖云：采购前核查具体型号；整条链路均本地接入后再验证断互联网运行。
